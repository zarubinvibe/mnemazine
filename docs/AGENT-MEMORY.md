# AGENT-MEMORY — слоёная память агентов и место личного vault в ней

Спроектировано Fable 5 по решению владельца 2026-07-25. Задача: агенты проектов пользуются знаниями
личного vault и пишут туда исследования, но общий корпус не превращается в мусор в их контексте — поэтому
память слоится, и каждый слой имеет свой канал доступа и свою дисциплину. Система работает и в
одиночной Мнемозине, и после интеграции во внешний агентный рой (рой дешёвых моделей: Kimi до 300 параллельных
агентов) — все гейты здесь код, не LLM, чтобы дешёвая модель исполняла их так же, как дорогая.

## Слои (от горячего к холодному)

| Слой | Что | Где живёт | Кто пишет |
|---|---|---|---|
| L0 сессия | рабочая память хода | контекст окна | сам агент |
| L1 агент | факты/уроки конкретного агента | auto-memory (`$HOME/.claude/projects/<proj>/memory/`) | агент |
| L2 проект | решения, инварианты, хэндоффы | repo проекта (`docs/`, `CONSTRAINTS.md`, handoff) | сессии проекта |
| L3 общая (внешний рой) | ошибки роя, чтобы не повторять | `learning/`, `CONSTRAINTS.md` внешнего роя | только координатор |
| L4 личный vault | глубокое знание владельца, тысячи нот | `$MNEMAZINE_VAULT` (Obsidian vault) | только конвейер Мнемозины |
| — интернет | не память, а источник | сеть | — |

Правило дисциплины: слой не тащится в контекст целиком — только целевой срез через запрос,
потому что «общие знания» в контексте рабочего агента — это мусор, который вытесняет задачу.

## L4: чтение — read-only MCP над графом, не файловый доступ

Агенты читают личный vault через graphify-MCP поверх уже собранного графа:

```json
{ "mcpServers": { "vault-graph": {
    "command": "python3",
    "args": ["-m", "graphify.serve", "/path/to/vault/graphify-out/graph.json"]
} } }
```

(шаблон — `config/mcp-vault.json`; инструменты: query_graph, get_node, get_neighbors, shortest_path,
graph_stats). Граф отстаёт от vault → это чинит обязательный `graphify --update` в хвосте каждого
прогона `/kb`, не ручной ритуал. Fallback без MCP (одиночный режим): `/kb find <запрос>` — librarian
с grep+embed+rerank.

**Поправка 2026-07-25 (замер, не рассуждение).** Seatbelt внешнего роя до `$MNEMAZINE_VAULT` не пробивается — это
решение осталось прежним, но следствие было описано неверно. MCP-сервер запускается ДОЧЕРНИМ процессом
бога и наследует его профиль, поэтому под seatbelt он открывает `graph.json` и получает
`Operation not permitted` — измерено профилем той же формы. Значит `vault-graph` работает только у
провайдера, чей MCP-процесс не завёрнут в `sandbox-exec`: сегодня это только `claude`. Во внешнем рое это
не пожелание, а отказ в `resolveCapabilities` до диспатча (`catalog/mcp.json` → `hostReadServers`,
`src/capabilities.ts` → `HOST_READ_PROVIDERS`), потому что выданный-но-EPERM инструмент бог молча
обходит. kimi/codex/openai читают личный vault не сами — через дайджест координатора (D8).

## L4: запись — только через воронку инбокса

Агент кладёт файл-заявку `agent-research--<project>--<slug>.md` в `$HOME/Desktop/Mnemazine Inbox/` —
это единственная законная дверь, потому что файл, положенный в раздел vault напрямую, минует census
и гейт полноты, не получает `run_id`/`verified` и ломает индексы.

**Поправка 2026-07-25 (замер).** Бог внешнего роя не может писать в инбокс сам: seatbelt денит запись всюду,
кроме его worktree (`touch "$HOME/Desktop/Mnemazine Inbox/x"` → `Operation not permitted`). Поэтому во
внешнем рое заявка пишется в `research/` worktree бога, а в инбокс её переносит координатор
(`src/research-inbox.ts`) — с валидацией имени, лимитом 256 KiB и штампом провенанса `god/run/время`,
который бог подделать не может. Для агентов вне внешнего роя (обычная сессия Claude Code без seatbelt)
правило прежнее — файл кладётся в инбокс напрямую. Конвейер обрабатывает заявку как
обычное сырьё: верифицирует, расставляет провенанс, пишет ноту `type: agent-research`
(`claim_status: provisional`) по NOTE-SPEC. В проверенный корпус агентская нота переходит только
операцией graduate после ревью — агентская верификация слабее владельческой.

## Протокол «старт разработки» (обязателен, не по желанию)

Перед реализацией фичи/исследованием агент проходит слои сверху вниз:

1. L2 + L3 — инварианты проекта и прошлые ошибки роя (не повторять уже оплаченное).
2. L4 — запрос в граф личного vault по теме (что владелец уже собрал; расхождение с нотой — сигнал, не помеха).
3. Интернет — свежее состояние мира (знание в личном vault может устареть).
4. Итог: рабочие выводы → L2 (docs/research проекта); durable-знание → заявкой в L4-инбокс.

Порядок именно такой, потому что каждый следующий слой дороже предыдущего, а конфликт слоёв
разрешается свежестью: интернет бьёт личный vault, личный vault бьёт устаревший док проекта — с пометкой в итоге.

## Что НЕ строим (решено, не переоткрывать)

- Фоновый «шёпот-агент», сам подмешивающий знания, — нет: явный конвейер строже и прозрачнее.
- Файловый доступ богов к `$MNEMAZINE_VAULT` через seatbelt — нет, см. выше.
- HTTP REST-порт над vault — нет, пока не появился агент без файловой системы и без MCP.
- Второй параллельный поисковый слой — нет до retrieval-eval: споры о поиске решают числа.

## Интеграция во внешний агентный рой (следующая фаза, не эта)

Мнемозина остаётся самостоятельным проектом; в другой проект семейства переезжают способности: `vault-graph` MCP
регистрируется в `catalog/mcp.json`, заявки в инбокс пишут боги через своё worktree-правило,
`/kb lint` и дедуп-кампании исполняет Kimi-рой (все проверки — код с exit-кодом, LLM только там,
где суждение: merge-вердикт, graduate-ревью). Файлы внешнего роя в этой фазе не трогаются.
